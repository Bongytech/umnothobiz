## Blocking

### 1. A `failed` payment can never recover — the bug this PR set out to fix survives in a new form

`umnotho/functions/src/payments.ts:265`

```ts
if (data.status !== 'pending' && !(data.status === 'expired' && event.status === 'paid')) {
  return;
}
```

`failed` is terminal here. Now look at what writes `failed`:

- **277–286** — a paid event whose payload has no usable `actually_paid` → `status: 'failed'`
- **289–299** — an underpayment beyond tolerance → `status: 'failed'`

If a provider ever sends `finished` without a usable amount (a malformed/partial IPN, or
a field rename upstream), the customer's payment is written off as `failed` and **no
later event can settle it**, because the guard above returns before the amount can be
re-evaluated. The reconciliation job added in this PR cannot rescue it either: it only
scans `status == 'pending'` (`index.ts:182-186`).

That is the same failure mode as finding 2 — paid customer, no plan, support ticket — just
triggered by a different edge.

**Suggested fix:** treat `failed` as recoverable when it was failed *for amount reasons*
and a later paid event carries a valid amount:

```ts
const recoverable =
  data.status === 'pending' ||
  (data.status === 'expired' && event.status === 'paid') ||
  (data.status === 'failed' &&
    event.status === 'paid' &&
    typeof data.amountReceived !== 'number');   // never actually received anything
if (!recoverable) return;
```

and widen the reconciliation query to include `failed` payments carrying a
`providerMessage` marker, so a provider-side correction is picked up automatically.

### 2. P0's test exit criterion is not met

The plan required: *“automated tests cover late and duplicate webhooks, provider/Firestore
failures, amount handling, and idempotent settlement.”*

What the branch adds is `functions/src/provider.test.ts` (55 lines, sandbox gate only) plus
two rules tests. There is **no test for `settlePayment` at all** — no late webhook, no
duplicate webhook, no missing amount, no overpayment, no transaction-failure path. Those
are exactly the regressions that got us here.

`settlePayment` is not exported (`payments.ts:252`), so it can't be unit-tested in
isolation. Either export it for tests, or add `payments.test.ts` against the Firestore
emulator, which `@firebase/rules-unit-testing` already supports in the repo.

Minimum set to satisfy the gate:

1. `finished` IPN arriving after `expiresAt` → `paid`, `latePayment: true`, plan extended.
2. duplicate `finished` IPN → one extension only.
3. paid event with no amount → `failed`, then a corrected event → `paid` (guards issue 1).
4. underpayment beyond tolerance → `failed`; overpayment → `paid` + `overpaid: true`.
5. transaction failure during settlement → `cryptoWebhook` answers 500 (not 200/400).

### 3. The signup notice fix is unreachable

`src/components/Auth.tsx:54-60` no longer navigates after `signUp`; it sets `notice`,
`canContinue`, and switches the form to login mode. But `App.tsx` wraps this route in
`PublicOnlyRoute`, which redirects to `/barter` as soon as `AuthContext.user` becomes
non-null — and `createUserWithEmailAndPassword` signs the user in immediately. So the
component unmounts and the “Continue to the market” button is never reachable. Finding 26
is still open, now with dead UI added.

**Suggested fix:** pass the notice through navigation state and render it on the
destination (`navigate('/barter', { state: { notice } })`), or use a toast provider.
That's the approach the plan itself suggested.

## Should fix (not merge-blocking)

### 4. Bidders are now locked into a negotiation

`firestore.rules:189` allows delete only while `status == 'Pending'`, and `MyBids.tsx:392`
renders “Withdraw offer” only for `Pending`. But `bids.ts` says a bidder may decline from
both `Pending` **and** `In Negotiation`, and the UI has no bidder decline button at all. Net
effect: once the owner clicks *Negotiate*, the bidder has no way out.

Either keep delete available in `In Negotiation`, or (better) add a bidder-driven
`Declined` transition: allow `status == 'Declined'` for the bidder in `isOwnerStatusChange`
(rename it), and render a “Decline” button for bidders.

### 5. The CSP blocks the fonts the page loads

`umnotho/firebase.json:40-41` sets `style-src 'self' 'unsafe-inline'` and
`font-src 'self' data:`, but `index.html:30-35` loads
`fonts.googleapis.com` (stylesheet) and `fonts.gstatic.com` (font files). Under
report-only this is noise; the moment it is enforced, the typography breaks.

Add `https://fonts.googleapis.com` to `style-src` and `https://fonts.gstatic.com` to
`font-src` — or self-host the two families and keep the tighter policy. Worth checking the
report-only violations after a deploy before flipping the header to enforcing.

### 6. Account deletion: 500-document cap and counterparty message loss

`functions/src/account.ts:48-52` uses `limit(500)` with no pagination. A user with more than
500 listings or bids leaves un-anonymised content behind (their name, offer text) against a
now-deleted UID. Loop with `startAfter` until exhausted, or process via a queue.

More importantly, `account.ts:60-69` sets `messages: []` on every affected bid. That erases
the *counterparty's* record of the negotiation, which they may need for a dispute. Suggest
replacing only the deleted user's messages with a redaction placeholder and keeping the
other party's side intact.

### 7. `USE_SECRET_MANAGER` is now mandatory in production, but nothing sets it

`functions/src/provider.ts:67-72` refuses to construct the NOWPayments provider outside the
emulator unless `USE_SECRET_MANAGER === 'true'`. The docs were updated (good), but
`deploy.yml` doesn't set that variable and the workflow doesn't check it. A deploy following
the repo's own instructions will ship functions whose checkout callable fails and whose
webhook returns **503** — silently, because `getProvider()` throws by design.

Either set `USE_SECRET_MANAGER=true` in the functions environment as part of the deploy
runbook, or derive the decision from the presence of bound secrets rather than a separate
flag that can drift.

### 8. Reconciliation backlog

`index.ts:182-186` processes at most 100 pending payments per hour with no continuation.
Under load, or after an outage, the backlog never drains. Loop until the query is empty
(with a safety cap), or page with `orderBy('createdAt')`.

### 9. gitleaks config: schema and scope

`.gitleaks.toml:4-18` uses the `[allowlist]` (singular) table. That is the pre-8.19 schema;
newer gitleaks releases expect `[allowlists]` and warn or ignore the old key depending on
version. `gitleaks/gitleaks-action@v2` installs its own pinned version, so this may fail or
silently pass. Pin the version explicitly (or the action's `GITLEAKS_VERSION`) and verify
`gitleaks detect` locally reports the same result.

Separately, allowlisting all of `docs/` is broad — a key pasted into a doc would go
unreported. Prefer path-specific exemptions.

### 10. Dead branch in `MyBids`

`src/components/MyBids.tsx:357-361`: the `Completed`/`Declined` paragraph is nested inside
`{open && …}`, and `open = isOpenBid(status)` is only `Pending`/`In Negotiation`. That
branch can never render. Harmless, but it will confuse the next reader — either drop the
outer guard or drop the branch.

### 11. Orphan invoice if the post-invoice update fails

`payments.ts:175-191`: if the `update()` that attaches `providerPaymentId` fails, the PR
throws `unavailable`, but the invoice exists at the provider and its id was never persisted
— so reconciliation cannot find it and the customer may pay an invoice nobody can settle.
Consider writing the provider payment id with a short retry loop, or making the doc update
the last thing that can fail silently (log + continue) rather than an error the user sees.
